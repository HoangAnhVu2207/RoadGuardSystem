# Compatibility considerations (documentation only)

A08-01 concerns a same-project, same-key, byte-identical detections/checksum fingerprint with different identifying fields. Runtime classification belongs in report/TRX; source explains an existing-job check before receipt, followed by identity/file guards only on an uncached execution. A different project has a different receipt scope. Shape-invalid fields can be rejected by DTO/service before lookup; not every changed field/input can replay.

PROPOSED follow-up under RF-10-05: agree callback identity domain and add regression cases for valid replay, all six omitted fields, cross-project independent acceptance, upstream rejection, changed fingerprint, stored failures, and persisted legacy receipts. Do not change production in this characterization task.

Adding identity fields to the fingerprint for the same operation/key would make retries of existing receipts compare a new hash against the stored old hash, potentially returning conflict for previously accepted requests. Old receipt OutcomeJson cannot reliably recover all missing identity fields (raw file, manifest, mode); do not silently infer original identity from a now-current mutable job. A separate operation version may create a fresh receipt/effect attempt against already completed jobs; a key namespace change also changes replay and deduplication semantics. Legacy fallback requires an explicit policy, not an unconditional retry that might duplicate effects.

Owner/provider decisions remain UNKNOWN: whether key is globally unique per event or reused per job/attempt; provider retry horizon and persisted receipts; operation version/key namespace or explicit legacy compatibility; serializer canonicalization/version, field ordering, GUID/decimal/case normalization; whether raw file identity or content identity governs replay. Current service normalizes detection GUID strings and emits Web JSON; general canonical serialization is not established by that implementation. No rollout policy, contract adoption, data migration, retention deletion or deployed-incident conclusion is chosen here.

HTTP validation controls and repository source behavior must both be retained in follow-up. This finding does not resolve late-A fencing CG11/RF10-R07 and does not establish exploitability, provider key collision frequency or deployed incidents.
