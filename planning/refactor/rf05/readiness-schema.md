# RF-05 decision authority and readiness (inactive proposal)

Three inputs have separate responsibilities. Historical FR/BR/US/PF/NFR source sections and their stable `*.Cnn` claims come from RF-04; `source_authority` and each claim's `authority` remain historical after confirmation. `planning/refactor/04-decision-index.json` records a newly accepted decision, its exact owner source, heading anchor, status line, interpretation, date/person when present, requirement scope and SHA-256 of each approved claim's UTF-8 content. `planning/refactor/04-readiness-decisions.json` requests the implementation scope and state. The generator validates all three before deriving `authority`, each claim's `current_authority`, `readiness`, and `implementation_readiness` in the crosswalk and product page.

The proposed decision index starts empty. It does not invent new acceptance or replace the preserved 32-44 table in `02-decision-register.md` and `docs/product/confirmed-decisions.md`. A future entry uses a stable ID and a Markdown source section with an exact `##` anchor, a line such as `Status: Accepted by <person> on <date>.`, and a table row `| ID | interpretation | scope |`. The index must reproduce that line and interpretation, give `confirmed_by` and `confirmed_at` values present in the status line, and name a requirement scope present in the table's third cell. A source path under `docs/product/` grants no authority by itself. Proposed/Unknown decisions fail.

For each approved requirement, `requirements[ID].claim_sha256` maps the exact affected claim IDs to SHA-256 of their historical text. The readiness registry's `approved_scopes` names the same decision ID, source plus anchor, interpretation, scope and claim IDs. It cannot extend the indexed scope. Editing or deleting a claim invalidates the approval; adding a claim prevents whole-row READY until it too is covered. Regeneration with the same inputs is stable and refuses silently dropped READY, DEFERRED or partial-scope registry entries.

`READY` requires coverage of all current claims, no remaining blocker in the registry entry, and nonempty `required_evidence` listing checks still to perform. Partial confirmation produces `PARTIALLY_CONFIRMED_BY_DECISION`; a requirement with an unconfirmed claim remains `BLOCKED` with `reason` and `checkpoint`. `DEFERRED` also needs both fields. Confirmation establishes requirement authority only; it says nothing about implementation, HTTP/schema compatibility or executed tests. The legacy `confirmed_reference` is an overlap hint, not claim-level acceptance.

The read-only `verify_repository_readiness.py --root .` compares actual source IDs and task mapping, every recorded input SHA-256, regenerated expected row content, and product-page authority/readiness markers. It never writes generated files. The 148 historical requirement count is a reported delta baseline, not a fixed equality gate. `test_readiness_flow.py` uses a disposable repository fixture and a simulated later owner decision; no fixture decision enters the real decision index.
