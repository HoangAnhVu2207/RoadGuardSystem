# Task delivery and verification

Record branch, HEAD, dirty paths, owner, exact allowed files/symbols, shared reservations, dependencies and a narrow verification plan. Read the relevant requirement and decision first, then current contract, caller, controller, service, repository/entity and tests. Separate behavior-preserving structure from public or data changes.

For HTTP work, use the observed Controller -> Service interface -> Repository interface seam documented in `planning/refactor/01-endpoint-inventory.md`. Controllers bind requests and map results; Services orchestrate actor, scope and business policy; Repositories handle EF/SQL/storage and atomic durability. This is a surveyed convention, not proof every existing implementation is exemplary. Keep a vertical slice through tests. Inspect transaction, idempotency, rowversion, outbox and worker paths when that slice writes data.

Choose the smallest tests that cover the changed risk. Documentation/tooling uses link, schema, patch and validator checks. Code changes need fresh affected builds/tests; authorization checks wrong actor/project, persistence checks isolated SQL, endpoint changes check actual HTTP status/body/headers and durable effect. Do not run data-writing tests against a shared database. Record executed/failed/skipped/not-run counts; no PASS from file presence or a fake producer/consumer alone.

When scope permits, update approved contract, Postman, `.http` and docs together; preserve existing consumer identifiers and compare compatibility. Never auto-update the FE lock or treat draft OpenAPI as canonical. Complete two concise review passes, fix in-scope findings, rerun invalidated checks, inspect final diff. Deliver on `anh-review` or `huy-review` with one assigned spec under `planning/development/` and a short PR summary: problem/result, base/HEAD and changed scope, both self-review passes, commands/results, decisions/blockers and BE/mock/external/deployment evidence. No seven-part RF report or separate coordination file is required. ChatGPT reviews the GitHub diff; distinguish that review from Codex self-review. Resume after rechecking HEAD and dirty changes; invalidate evidence affected by drift. No framework expansion, package upgrade or unrelated refactor. Steps already authorized by the spec need no repeated approval.
