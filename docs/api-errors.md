## Overview and RFC 7807/9110 Standard

The RoadGuard System API enforces a uniform, machine-readable error-handling contract across all HTTP endpoints. Standard API 4xx/5xx error responses returned by the backend conform to **RFC 7807 / RFC 9110 Problem Details for HTTP APIs** using the standardized media type:

```http
Content-Type: application/problem+json
```

*(Note: Specialized endpoints or protocols with an explicitly documented alternate contract—such as raw streaming endpoints, binary file downloads, or simple process liveness probes like `/health`—are exempt from the ProblemDetails contract).*

### Implementation Baseline vs. Target Policy
- **Current Baseline (P1-01), extended by P1-10:** The platform enforces uniform ProblemDetails error serialization for HTTP status codes **400, 401, 403, 404, 405, 409, 415, and 500**. P1-10 supplies the authentication-specific 401/403/409 mappings and correlation IDs.
- **Downstream Implementation Target:** Project-authorization 403 mappings remain assigned to P1-12, while 422 and domain-specific conflict mappings remain assigned to their corresponding use-case tasks.

## Standard Error Envelope Schema

The error payload serialized to the client contains standard RFC 7807 properties supplemented by mandatory system extension fields:

```json
{
  "type": "https://httpstatuses.io/400",
  "title": "Validation Failed",
  "status": 400,
  "instance": "/api/v1/surveys",
  "code": "validation_error",
  "correlationId": "4f18d780-e83c-41c5-8472-f19b22a07c91",
  "errors": {
    "sectionId": [
      "The sectionId field is required."
    ]
  }
}
```

### Envelope Field Definitions

| Field | Type | Presence | Description |
|---|---|---|---|
| **`status`** | Integer | Mandatory | The HTTP status code generated by the origin server (e.g., `400`, `401`, `404`, `500`). Must match the response HTTP status line. |
| **`title`** | String | Mandatory | A short, human-readable summary of the problem type. Written in English; suitable for developer diagnostics. |
| **`type`** | String (URI) | Mandatory | An absolute URI reference identifying the problem type specification (e.g., `https://httpstatuses.io/400`). |
| **`instance`** | String (URI) | Mandatory | An absolute path reference identifying the specific endpoint instance where the request occurred (e.g., `/api/v1/surveys`). |
| **`code`** | String | Mandatory | A stable, machine-readable error code in ASCII lowercase `snake_case`. Used by client applications for programmatic error dispatch and localization. |
| **`correlationId`** | String (UUID) | Mandatory | A globally unique UUID identifying the request lifecycle. Matches the `X-Correlation-ID` HTTP response header and structured server logs. |
| **`errors`** | Object | Conditional | A dictionary mapping invalid property names to arrays of error messages. Present **only** on validation errors (HTTP 400 / 422). Omitted for general errors. |

## Error Code Naming Rules and Taxonomy

To ensure long-term stability and prevent ambiguous client handling, all error codes must comply with the following conventions:

1. **Character Set & Casing:**
   - Error codes must use strictly **ASCII lowercase alphanumeric characters and underscores (`snake_case`)**.
   - Uppercase letters, spaces, hyphens, camelCase, and special characters are strictly prohibited.

2. **Platform vs. Domain Error Taxonomy:**
   - **Platform Errors:** Foundational infrastructure error codes (defined in `RoadGuardSystem.API/Constants/ApiErrorCodes.cs`) retain their established short names for backward compatibility (e.g., `validation_error`, `not_found`, `internal_error`).
   - **Domain Errors:** New business and domain error codes must follow a hierarchical naming pattern:
     ```
     <domain>_<reason>
     ```
     *Examples:* `auth_invalid_credentials`, `project_access_denied`, `survey_already_confirmed`.
   - **Action Disambiguation:** When multiple distinct actions within the same domain produce differing failure conditions for the same resource, the action verb may be included for clear disambiguation:
     ```
     <domain>_<action>_<reason>
     ```
     *Examples:* `defect_verify_already_closed`, `repair_batch_assign_capacity_exceeded`.

3. **Invariable Representation:**
   - Error codes are immutable identifiers. They must **never** embed dynamic values, entity IDs, user inputs, database keys, or localized text (e.g., `survey_123_not_found` is prohibited; use `survey_not_found` with the instance URI).

## HTTP Status Code Mapping

The API strictly adheres to standard REST and HTTP semantics. Status codes must not be overloaded or interchanged:

| HTTP Status | Semantics & Usage Criteria | Typical Error Code |
|---|---|---|
| **400 Bad Request** | Syntactic errors, malformed JSON bodies, unparseable parameters, or unsupported API version segments. | `validation_error`, `unsupported_api_version` |
| **401 Unauthorized** | Unauthenticated request. Authentication credentials are missing, expired, cryptographically invalid, or the session was revoked. | `auth_unauthorized`, `auth_session_revoked` |
| **403 Forbidden** | Authenticated user lacks required role permissions, or is not an active member of the requested project (server-side project membership failure). | `access_forbidden`, `project_access_denied` |
| **404 Not Found** | The requested URL route, API endpoint, or specific aggregate entity ID does not exist. | `not_found`, `<domain>_not_found` |
| **405 Method Not Allowed** | The HTTP method (verb) used is not supported for the matched route template. | `method_not_allowed` |
| **409 Conflict** | State conflicts: optimistic concurrency version mismatch, idempotency key collision, or invalid domain state transitions. | `concurrency_conflict`, `duplicate_request`, `invalid_state_transition` |
| **415 Unsupported Media Type** | The request `Content-Type` header is not supported by the endpoint (e.g., sending `text/plain` to a JSON endpoint). | `unsupported_media_type` |
| **422 Unprocessable Content** | Business/semantic validation failures. The payload is syntactically valid JSON and passes schema validation, but violates domain business rules. | `<domain>_validation_failed`, `<domain>_business_rule_violated` |
| **500 Internal Server Error** | Unexpected, unhandled server-side exceptions. Masked completely to prevent information leakage. | `internal_error` |

## Registry of Normative Error Codes

The following six platform error codes are currently published and normative. They are implemented in `RoadGuardSystem.API/Constants/ApiErrorCodes.cs` and verified by API platform tests:

| Error Code | HTTP Status | Meaning and Trigger |
|---|---|---|
| **`validation_error`** | 400 | The request payload failed JSON deserialization, model binding, or property validation constraints. |
| **`unsupported_api_version`** | 400 | The request targeted a numeric API version segment that is not supported by the platform (e.g., `/api/v99.0`). |
| **`not_found`** | 404 | The requested route does not match any registered endpoint or route template. |
| **`method_not_allowed`** | 405 | The HTTP verb is not allowed for the matched route (e.g., `POST` to a read-only endpoint). |
| **`unsupported_media_type`** | 415 | The request payload `Content-Type` is not supported (e.g., missing `application/json`). |
| **`internal_error`** | 500 | An unhandled exception occurred during request processing. Always accompanied by a generic public message. |

Authentication and identity endpoints add the following stable domain codes. They preserve the same lowercase `snake_case` and correlation-ID requirements; credential, token, hash, and persistence details are never included in the response:

| Error Code | HTTP Status | Meaning and Trigger |
|---|---:|---|
| **`auth_invalid_credentials`** | 401 | Username/password or refresh credential cannot be accepted without revealing whether the account exists. |
| **`auth_password_change_required`** | 403 | Credentials are valid but the account is flagged for a mandatory password change; no business-capable token is issued. |
| **`auth_unauthorized`** | 401 | The request has no valid authenticated identity or authoritative session/user validation failed. |
| **`auth_session_revoked`** | 401 | The session/token family is expired, revoked, replayed, or carries a stale role snapshot. |
| **`auth_concurrency_conflict`** | 409 | A refresh or other authentication workflow lost an optimistic-concurrency race. |
| **`access_forbidden`** | 403 | An authenticated actor lacks the required global Supervisor authority for the requested identity action. |
| **`identity_user_not_found`** | 404 | The target identity does not exist; no credential or account detail is disclosed. |
| **`identity_user_inactive`** | 409 | The target identity is suspended or otherwise not eligible for an administrative password reset. |
| **`duplicate_request`** | 409 | An idempotency operation ID was previously used with a different request fingerprint. |
| **`identity_email_conflict`** | 409 | The requested profile email is already assigned to another user. |

## Security and Information Disclosure Rules

To eliminate information disclosure vulnerabilities across all deployment environments:

1. **Suppression of Internal Exceptions and Stack Traces:**
   - Stack traces, internal CLR exception type names (`System.NullReferenceException`, `SqlException`), database query fragments, and server file paths must **NEVER** be serialized into ProblemDetails responses.
   - This invariant is enforced globally in `RoadGuardSystem.API/Extensions/ServiceCollectionExtensions.cs` across all environments (Development, Staging, Production).

2. **Secret and PII Masking:**
   - Error messages, parameters, and error codes must never contain secrets, passwords, connection strings, auth tokens, or personally identifiable information.

3. **Correlation Diagnostics:**
   - All diagnostic details are written securely to server-side structured logs tagged with the `correlationId`. Developers and operators investigate failures by looking up the `correlationId` in telemetry stores.

## Versioning, Evolution, and Deprecation Policy

1. **Evolution & Compatibility Reviews:**
   - As new use cases are developed (e.g., in Tasks P1-10, P1-11, P1-12), new domain error codes may be registered.
   - Adding or altering an error code on an existing endpoint is not inherently transparent to client implementations. Consequently:
     - Client applications must be designed to be resilient, treating any unrecognized `code` gracefully by falling back to the standard HTTP `status` code.
     - Any modification or addition to an endpoint's published error codes must undergo an explicit API compatibility review before release.

2. **Immutability of Published Codes:**
   - Once an error code is published and consumed by mobile or web clients, its text string and semantic meaning become **immutable**.
   - An error code must never be renamed or repurposed to mean something different.

3. **Deprecation Process:**
   - If a business condition becomes obsolete, the associated error code must be formally marked as `Deprecated` in this specification with a documented migration path.
   - The required duration for deprecation notices and sunsetting windows is an unresolved policy that will be decided by the Product Owner prior to the first public API release.
