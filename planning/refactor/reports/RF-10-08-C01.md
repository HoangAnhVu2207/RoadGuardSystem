## Findings

### F-RF-10-08-C01-01: Upload Complete Precondition Pattern Differs from Survey Postpone

**Severity:** Moderate (affects test design, not production bug)

**Description:**
Upload Complete checks RowVersion precondition inside idempotency handler (line 247-249) but THROWS `UploadConcurrencyException` on failure, causing transaction rollback with NO idempotency record stored. Survey Postpone stores concurrency failure in outcome JSON (line 65) and commits transaction. This means Upload Complete retry with stale version will execute handler again (no replay), while Survey Postpone retry will return stored failure (replay).

**Evidence:**
```csharp
// Upload line 247-249: throws on stale
if (!session.RowVersion.SequenceEqual(Convert.FromBase64String(request.ExpectedVersion)))
{
    throw new UploadConcurrencyException();
}
// Handler rolls back, NO record created

// Survey line 63-66: stores failure
if (!plan.RowVersion.SequenceEqual(Convert.FromBase64String(request.ExpectedVersion)))
{
    return (Guid.NewGuid(), JsonSerializer.Serialize(new StoredPlanOutcome(
        SurveyV2PersistenceStatus.ConcurrencyConflict, null)));
}
// Handler commits, record exists with stored failure
```

**Impact:**
- Upload Complete is NOT a pure Pattern A example for Gap 5 testing
- Gap 5 test (stored precondition outcome replay) MUST use Survey Postpone only
- Pattern classification needs refinement: Pattern A (stores), Modified Pattern A (throws)

**Recommendation:**
Retain both approaches during characterization. Future unification decision (Q-RF02-X) can assess whether Upload should adopt Survey's store-failure pattern or keep current throw-rollback behavior.

### F-RF-10-08-C01-02: Three Distinct Authorization/Precondition Ordering Patterns

**Severity:** Low (design observation, not defect)

**Description:**
Production code implements three distinct patterns for authorization/precondition ordering relative to idempotency:
- **Pattern A (Survey Postpone):** Auth → Idempotency → Precondition inside, stores failure
- **Pattern B (Project Create):** Auth → Precondition → Idempotency, fails before idempotency
- **Pattern C (Survey Task):** Auth → Idempotency → Eligibility inside, throws on failure

**Impact:**
Different patterns produce different replay behavior:
- Pattern A: Precondition failures are stored, replay returns stored failure
- Pattern B: Precondition failures never reach idempotency, retry re-checks precondition
- Pattern C: Precondition failures throw exceptions, no record stored

**Recommendation:**
Document patterns in operation matrix. Future refactor (if R01 moves from RETAIN) should consider consolidating to single pattern, but current diversity serves different business semantics (PM eligibility is persistent vs RowVersion changes frequently).
