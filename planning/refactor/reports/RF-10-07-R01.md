## 2. Current implementation characteristics

### InspectionTaskQueryService
- **Single operation:** `ListAssignedAsync` - read-only query
- **Authorization:** RepairCrew role check (line 35)
- **Scope filtering:** Project membership via `IProjectScopeGuard` with per-project caching (lines 58-74)
- **Cursor pagination:** Custom Base64 encoding of `(DueAt.UtcTicks, Id)` tuple (lines 96-135)
- **Response projection:** Hardcoded `"MEASURE_ONLY"` mode, null `policyVersionId`, uppercase status, Base64 RowVersion (lines 76-84)
- **No persistence:** Read-only, no write operations

### InspectionTaskReadRepository
- **Single query:** `ListAssignedAsync` - EF Core join between tasks and assignments
- **Filtering:** AssignedToUserId + Active assignment status (lines 30-31)
- **Cursor support:** `WHERE (DueAt > @after OR (DueAt = @after AND Id > @afterId))` (lines 45-49)
- **Pagination:** Fetch `limit + 1` rows, `hasMore` flag, return last DueAt/Id for next cursor (lines 51-80)
- **Ordering:** `ORDER BY DueAt ASC, Id ASC` (lines 52-53)

## 3. Comparison with similar patterns

### SurveyV2Service differences
- **Mixed operations:** Plan creation, postponement, task creation, task retrieval, task listing
- **Multiple roles:** ProjectManager (create), DroneOperator (list mine), Supervisor (read)
- **Scope checking:** Inline `InScope` helper (line 202), not cached per-project
- **Cursor handling:** Repository-provided; no explicit encode/decode in service
- **No status result enum:** Returns nullable DTO or throws; no `SurveyV2ServiceStatus` for GET operations
- **Idempotency:** Fingerprint-based replay protection for writes

### Structural differences preventing extraction
1. **Authorization granularity:** InspectionTask restricts to single role (RepairCrew); SurveyV2 supports PM/Supervisor/Operator with different filtering logic
2. **Scope caching strategy:** InspectionTask caches per-project in single iteration; SurveyV2 calls per-operation without caching
3. **Response transformation:** InspectionTask hardcodes mode/policyVersion; SurveyV2 returns stored projection
4. **Cursor ownership:** InspectionTask service owns encoding format; SurveyV2 delegates to repository
5. **Result typing:** InspectionTask uses `InspectionTaskQueryResult` with status enum; SurveyV2 returns nullable DTO

## 4. Extraction risk analysis

### If scope filtering were extracted to shared abstraction:

**Authorization complexity:**
- Current: Single role check + scope guard; 4 lines (lines 30-38)
- Abstraction would need: Role set parameter, different filtering logic per consumer, authorization strategy pattern
- **Risk:** Over-abstraction increases cognitive load; each query has unique authorization rules

**Projection coupling:**
- InspectionTask: Service maps repository view → response DTO with domain logic (hardcoded mode, null policy)
- SurveyV2: Service returns stored JSON projection, minimal mapping
- **Risk:** Shared projection would couple unrelated business rules

**Cursor format stability:**
- InspectionTask: `(DueAt, Id)` tuple matches `ORDER BY DueAt, Id`
- SurveyV2: Repository-provided cursor, format not exposed to service
- **Risk:** Extracting cursor logic assumes stable ordering across queries; brittle if ordering requirements diverge

**Pagination semantics:**
- Both use `limit + 1` fetch + `hasMore` flag
- InspectionTask returns `nextCursor` only when `hasMore`; SurveyV2 returns repository cursor directly
- **Similarity:** Minor; does not justify abstraction overhead

## 5. Decision: RETAIN

**Recommendation:** Do not extract. Current duplication is superficial; core logic differs.

**Rationale:**
1. **Authorization divergence:** Role restrictions and scope filtering rules are domain-specific, not infrastructure concerns
2. **Single-operation services:** InspectionTaskQueryService has one method; abstraction overhead exceeds duplication cost
3. **Cursor format ownership:** Service-level cursor encoding documents pagination contract explicitly; hiding it in abstraction obscures API stability
4. **Projection logic:** Response mapping contains domain rules (mode, policyVersion); shared abstraction would couple unrelated business logic
5. **Low change frequency:** Query services are stable; read-side changes infrequent after characterization

**Concrete duplication:**
- Cursor encode/decode (30 lines): Copy-paste acceptable; format is API contract, not implementation detail
- `IProjectScopeGuard` loop (15 lines): Domain-specific caching strategy, not infrastructure

**Reassessment triggers:** Reassess when equivalent duplication or a concrete extraction benefit is established, preserving authorization, projection, cursor ordering and wire encoding. No numeric caller threshold applies.

## 6. Alternative considered: Repository-level cursor abstraction

**Proposal:** Extract `ICursorPaginationRepository<TView, TCursor>` with:
- `EncodeCursor(TCursor)` / `DecodeCursor(string)` interface
- Repository implementations provide cursor encoding logic

**Rejection reasons:**
1. **Format is API contract:** Cursor encoding (Base64 of `ticks|guid`) is part of HTTP API; changing it breaks existing clients
2. **Low reuse:** Only 2 query repositories identified; abstraction overhead not justified
3. **Testing impact:** Interface adds mock complexity; current encode/decode are static methods easily unit-tested
4. **Ordering coupling:** Cursor format depends on `ORDER BY` clause; abstraction hides this dependency, increasing error risk
