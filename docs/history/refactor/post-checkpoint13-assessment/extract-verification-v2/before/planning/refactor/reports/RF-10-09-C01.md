## 2. Current Implementation Characteristics

### NotificationsController (HTTP Inbox)

**Three endpoints:**
1. `GET /api/v1/notifications/{id}` (lines 26-49)
   - Authorization: `[Authorize]` JWT bearer token
   - Actor extraction: `User.FindFirstValue(JwtRegisteredClaimNames.Sub)`
   - Recipient scope: calls `NotificationService.GetAsync(notificationId, actorUserId)`
   - Returns 404 if notification not found OR belongs to different user
   - Projection: id, message (body), resourceId (sourceEntityId), read boolean, occurredAtUtc, version (Base64 RowVersion)
   - ETag header: `"\"{version}\""` format

2. `GET /api/v1/notifications` (lines 52-72)
   - Query parameters: cursor (optional), limit (1-100, default 20)
   - Recipient scope: calls `NotificationService.ListAsync(actorUserId, cursor, limit)`
   - Returns: items array + nextCursor (only when hasMore)
   - Ordering: DESC by OccurredAtUtc

3. `POST /api/v1/notifications/{id}/read` (lines 74-132)
   - Requires headers: `Idempotency-Key`, `If-Match` (version)
   - Version extracted from If-Match: removes quotes, validates Base64
   - Returns 400 if headers missing, 412 if version mismatch, 409 if idempotency conflict
   - Success: returns notification with updated read status and new version

All routes use ProblemDetails with correlationId for errors.

### NotificationService (Service Layer)

**GetAsync** (lines 20-34):
- Validates actorUserId not empty
- Calls repository with recipient scope
- Returns 404 if not found (recipient filter at repository level)

**ListAsync** (lines 36-72):
- Limit validation: 1-100
- Cursor decoding: Base64 → JSON → `{OccurredAtUtc, Id}` tuple (lines 124-149)
- Cursor encoding: `{OccurredAtUtc, Id}` → JSON → Base64 (line 125)
- Delegates pagination to repository
- Returns nextCursor only when hasMore flag true

**MarkReadAsync** (lines 74-120):
- Fingerprint calculation: SHA256 of `notificationId|version` (lines 92-93)
- Wraps IdempotencyOperationService for transaction + replay detection
- Version mapping: Base64(notification.RowVersion) (line 122)
- Status enum: Success, NotFound, StaleConcurrency, IdempotencyConflict

### NotificationPersistenceService (Repository Layer)

**GetAsync** (lines 20-37):
- SQL: `WHERE RecipientUserId = @actorUserId AND Id = @notificationId`
- AsNoTracking query
- Returns null if not found or wrong user (same result, authorization boundary)

**ListAsync** (lines 39-84):
- Base query: `WHERE RecipientUserId = @actorUserId`
- Cursor filtering: composite `(OccurredAtUtc > after) OR (OccurredAtUtc = after AND Id > afterId)` (lines 50-70)
- Ordering: `ORDER BY OccurredAtUtc DESC, Id DESC` (stable sort)
- Fetch: `Take(limit + 1)` for hasMore detection
- Returns: items (up to limit), hasMore flag, lastOccurredAt, lastId for next cursor

**MarkReadAsync** (lines 86-149):
- Wraps IdempotencyOperationService.ExecuteAsync
- Inner function: loads notification with tracking, validates version, calls `notification.MarkRead()`, saves
- Concurrency exception handling: returns StaleConcurrency status
- Replay detection: deserializes stored outcome JSON, returns existing result

### NotificationOutboxConsumer (Outbox → Inbox)

**Consumer name:** `"notification-inbox"` (constant line 13)

**ConsumeAsync** (lines 17-50):
- Delegates to `ConsumerEffectService.ProcessAsync`
- Effect function: single `_context.Notifications.Add(notification)` without SaveChanges (line 44)
- Returns `NotificationDeliveryResult` with status (Recorded/Replayed) and notificationId
- ConsumerEffectService handles transaction commit, ConsumerEffectReceipt creation, and replay detection

**Replay behavior:**
- First call: effect executes, receipt created, returns Recorded
- Subsequent calls: effect skipped, returns Replayed with same notificationId from receipt

### OutboxWorkRepository (Lease/Retry Infrastructure)

**TryLeaseNextAsync** (lines 33-77):
- SQL with `UPDLOCK, READPAST` (lines 40-48)
- Filter: `DeliveryStatus NOT IN (Completed, DeadLetter)` AND `DeliveryAttemptCount < maxAttempts` AND `(LeaseExpiresAtUtc IS NULL OR LeaseExpiresAtUtc <= now)`
- Ordering: `NextAttemptAtUtc ASC` (processes oldest pending first)
- Calls `AcquireLease` if message found

**AcquireLease** (lines 79-98):
- Increments `DeliveryAttemptCount`
- Sets `LeaseOwner` (worker instance ID)
- Sets `LeaseExpiresAtUtc` (now + leaseDuration)
- Status remains Pending or becomes Leased (implementation detail)

**CompleteAsync** (lines 101-109):
- Validates lease owner matches
- Sets status to Completed
- Clears lease owner and expiry
- Clears error message

**RetryAsync** (lines 111-138):
- Validates lease owner matches
- Checks `DeliveryAttemptCount >= maxAttempts`
- If max reached: status → DeadLetter, sets LastErrorMessage
- If not max: schedules next attempt with exponential backoff, status → Pending
- Clears lease owner and expiry

### Producers (Event → Outbox)

**SurveyAssignmentPersistenceService.ReassignAsync** (lines 84-114):
- Creates `"survey_request.reassigned"` outbox message (lines 100-110)
- CorrelationId: surveyRequestId
- PayloadJson: includes old assignment ID, new assignment ID, reassignment reason
- Created within IdempotencyOperationService transaction boundary

**PrimaryProjectManagerPersistenceService** (lines 165-167):
- Creates `"project.primary_pm_reassigned"` outbox message
- CorrelationId: projectId
- PayloadJson: includes membership IDs

**Other producers identified:**
- DetectionReviewPersistenceService (defect detection events)
- ProcessingV2PersistenceService (`"processing_job.dispatch"`, `"validation_run.dispatch"`)

## 3. Dispatcher Investigation

### Search Results

**Attempted searches:**
1. `rg -i "BackgroundService|IHostedService" --type cs` → No matches calling IOutboxWorkRepository
2. `rg "IOutboxWorkRepository" --type cs -A 5` → Found interface, implementations, but no active caller in services
3. `find . -name "*Worker.cs" -o -name "*Dispatcher.cs" -o -name "*Scheduler.cs"` → Found UploadVerificationWorker, ValidationRunWorker

**Workers inspected:**

**UploadVerificationWorker:**
- Pattern: calls `IUploadService.ProcessOneVerificationAsync` in a loop
- Does NOT use IOutboxWorkRepository
- Different processing model (direct service call, not outbox-based)

**ValidationRunWorker:**
- Registered in DI container
- Uses different mechanism (not examined in detail, but does not appear in IOutboxWorkRepository caller search)

### Conclusion: NO DISPATCHER FOUND

No BackgroundService or IHostedService in the production codebase actively calls `IOutboxWorkRepository.TryLeaseNextAsync` to process outbox messages. The lease/retry infrastructure exists and is tested at the repository boundary, but is not currently invoked by a scheduled worker.

**Implications:**
- Outbox messages remain in Pending status indefinitely
- NotificationOutboxConsumer.ConsumeAsync is never called automatically
- Lease acquisition, retry scheduling, and DeadLetter transitions are not exercised in production
- This is an architectural gap, not a test coverage gap

## 5. Verified Behavior

### HTTP Inbox Authorization and Projection

**Verified:**
- GET single notification: recipient 200 OK, outsider 404
- GET list: recipient-only results, outsider notifications excluded
- Projection fields: id, message (maps to Body), resourceId (maps to SourceEntityId), read boolean (ReadAt != null), occurredAtUtc, version (Base64 RowVersion)
- ETag header matches version field
- GET operations are immutable (no SQL side effects)

**NOT_VERIFIED:**
- Cursor format stability across API versions (no versioning policy tested)
- Malformed cursor comprehensive edge cases (basic validation only)
- Large result set pagination performance (not measured)

### SQL Lease/Receipt/Retry

**Verified (at repository boundary):**
- TryLeaseNextAsync acquires lease with UPDLOCK+READPAST
- AcquireLease increments DeliveryAttemptCount, sets LeaseOwner/LeaseExpiresAtUtc
- CompleteAsync validates lease owner, transitions to Completed
- RetryAsync schedules next attempt or transitions to DeadLetter after maxAttempts
- NotificationOutboxConsumer replay returns Replayed status, single notification persisted, single receipt

**NOT_VERIFIED (no dispatcher):**
- Lease expiry and re-acquisition in production
- Retry loop execution with exponential backoff timing
- DeadLetter transition via dispatcher hitting maxAttempts
- NextAttemptAtUtc scheduling accuracy
- Real message delivery end-to-end timing

### Dispatcher/Scheduler/Provider Reachability

**NOT_VERIFIED:**
- No production BackgroundService or IHostedService found calling IOutboxWorkRepository
- Outbox messages remain in Pending status without active processing
- Lease/retry infrastructure tested at repository level only, not proven via real dispatcher
- Notification delivery timing cannot be characterized without dispatcher

## 6. Decision: CHARACTERIZATION COMPLETE with documented limitations

**Recommendation:** Accept characterization as complete for BOX 2 scope. The missing dispatcher is an architectural gap to be addressed separately, not a refactoring requirement.

**Rationale:**
1. **HTTP inbox behavior fully characterized:** Authorization, projection, pagination, mark-read idempotency with version checking all verified with owned SQL evidence
2. **Outbox pattern infrastructure verified:** Consumer replay protection, producer→outbox linkage, lease/retry repository methods tested at their boundaries
3. **Dispatcher absence documented:** Extensive search found no active caller; this is a known limitation, not a characterization failure
4. **Repository-direct proof is acceptable:** Tests directly invoke consumer and repository methods; this is valid for characterizing their behavior, though not equivalent to end-to-end delivery proof
5. **Reuse of existing evidence:** RF-08 P207 and P2 tests already cover persistence and basic HTTP scenarios; new tests focus on gaps (cursor pagination, conflict detection, producer linkage)

**Concrete characterization:**
- 5 focused tests covering inbox GET/List, mark-read mutations, consumer replay, producer→outbox linkage
- Fresh SQL snapshots with explicit field assertions (NotificationSnapshot record)
- Negative tests for wrong-user/stale-version scenarios
- Idempotency and conflict detection with Idempotency-Key header

**Documented limitations (NOT_VERIFIED):**
- Dispatcher/scheduler not found in production code
- Real delivery timing and retry loop execution
- DeadLetter transition via dispatcher reaching maxAttempts
- Cursor format stability and comprehensive edge cases
- External consumer integration (Web/Android/AI)

**Reassessment triggers:**
- Dispatcher implementation added (requires new end-to-end delivery tests)
- External consumer integration begins (requires client-side evidence)
- Notification retention/delete/reports implemented (Q-RF02-08 decision)
