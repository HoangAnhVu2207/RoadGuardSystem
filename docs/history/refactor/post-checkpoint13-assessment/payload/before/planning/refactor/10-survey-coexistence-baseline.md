`SurveyPlanningController` has no plan read route. The shared mutation path is `PostponePlan`/`Postpone`, not a cross-family GET. `SurveyPlanConfiguration` maps SQL rowversion; old writes do not accept `If-Match`. Both repositories use `IdempotencyOperationService` transactions and append audit rows; no plan create/postpone outbox producer is visible in these methods. Target correctness remains UNKNOWN pending Q-RF02-03, regardless of characterization result.

Source constraints for interpreting the plan test: both `SurveyPlanningService` and `SurveyV2Service` require a scoped ProjectManager for plan writes; `SurveyPlan.Postpone` rejects Completed/Cancelled but accepts Planned and already-Postponed. Old plan fingerprint hashes project/road/version, supplied start/end/type/output, or project/plan/new start/reason for postpone. V2 create hashes normalized project/scope/plannedAt/type; V2 postpone hashes plan/reason/expectedVersion. `IdempotencyOperationService` keys receipts by actor, nullable project, operation name and key; old postpone supplies project while V2 postpone supplies null. This is source/SQL behavior, not a cross-family dedup policy.

For `SurveyRequests`, old `CreateRequest` can reference a plan ID and creates a new request ID but offers no old read/mutate-by-request-ID route. V2 `CreateTask` creates a request plus assignment/scope rows; `GetTaskAsync` joins `SurveyAssignments` by request ID, and V2 task mutations use that ID. A freshly old-created request has no assignment from `CreateRequest`, so V2 read cannot find it through that join unless a separate assignment flow later adds one. There is no reverse old route to act on a V2 request ID. The HTTP same-row proof below is deliberately about `SurveyPlans`; request/task cross-family behavior and assignment lifecycle remain outside its tested conclusion.
