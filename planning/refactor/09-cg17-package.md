## Candidate sequence and compatibility gate

1. **Characterization START:** inspect current source/wire and run fixture-owned HTTP/SQL boundary tests and test-only DDL rehearsal under the existing R/C authorization. No deployed audit is needed for these local actions. **Implementation START:** obtain scoped public/schema approval, consumer versions and deployment order before editing active code/schema. **RELEASE/cutover:** obtain authorized deployed aggregate row/catalog audit and a real old/new binary matrix before deployment DDL or large writes. Keep max `int.MaxValue` in the current service and advertised contract until its separate implementation gate.
2. **Pre-deploy compatibility:** a test-only SQL experiment added computed `SizeBytes64 AS CONVERT(bigint,SizeBytes)` for existing rows without firing the immutable trigger; a future approved reader may use that for transition. This is a candidate, not a tested production adapter. Old binaries keep reading the `int` base until they are retired. New binaries must be tested against both old and widened SQL, not assumed compatible from CLR `long` alone.
3. **Schema candidate:** on isolated migrated SQL, dropping the computed candidate and size check, widening `Files.SizeBytes` to `bigint NOT NULL`, then recreating check/computed projection preserved an in-range row and left `TR_Files_Immutable` enabled. A new 8 GiB metadata row was inserted. This is **test-only DDL**, not an EF migration or deployed-schema proof. A future production migration should use its own ordered DDL and verify dependent objects.
4. **Cutover:** block large uploads until every old `int` reader/writer is removed or routed away, new reader/writer and external consumers pass contract tests, and an approved backup/forward-repair plan exists. The test demonstrated current EF `int` reader fails even on an old in-range row once SQL becomes `bigint`; a rolling mixed-binary deployment across widening is unsafe without a proven adapter.
5. **Large-write gate:** only then permit `> int.MaxValue` and at most 8 GiB for video. Rehearse `int.MaxValue`, `int.MaxValue + 1`, 8 GiB, `8 GiB + 1`, zero/negative and other purposes at HTTP, SQL and storage boundaries separately. After a value exceeds `int.MaxValue`, old SQL/CLR rollback cannot represent it. Disable new writes and use forward repair or an approved restore/replay strategy; do not claim simple down-migration is safe.

## Rehearsal evidence and limits

`tests/RoadGuardSystem.IntegrationTests/Infrastructure/Rf09TransitionRehearsalTests.cs` uses RF-06-owned Testcontainers SQL and all 37 current EF migrations. Its generic `Rf09SizeProbe` candidate backed up **before** expansion, backfilled two old rows in batches of one, simulated interruption/resume, reran idempotently, stored `int.MaxValue + 1`, 8 GiB and 8 GiB + 1 as `bigint`, rejected zero/negative, and restored the pre-change backup into a second fixture-owned DB. It compares ordered key/value rows, SHA-256 digest, migration count, absence of new column and the original synthetic `Files` row. A separate case widens real migrated `Files` in its disposable DB, verifies the immutability trigger and demonstrates old EF reader failure. These are metadata/SQL/reader proofs, **not** HTTP validation, storage transfer, deployed-row audit, production migration, measured RPO/RTO or external consumer acceptance. The generic backfill is not a plan to update immutable `Files` rows.
